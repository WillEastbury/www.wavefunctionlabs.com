Speed is a side effect

A short essay on what happens when you stop adding layers and start removing them.

simplicity · throughput · TLS · cloud · engineering principles
Wait… what?

The entire production HTTPS stack serving this site — TLS 1.3, HTTP, every header, every body, every compressed variant, the metrics endpoint — uses less RAM than an empty Python interpreter sitting at a blank prompt.

No Flask. No Django. No app. Just python3, doing nothing. That's the bar this entire site clears, while saturating a one-gigabit pipe at 20,000+ requests per second.

TL;DR

We rebuilt this site to serve TLS itself, with no proxy in front of it. One process. One core. It now does 20,000+ requests per second, the network runs out before the CPU does, and the whole container lives in about 3 MiB of RAM. We didn't make anything faster — we just deleted the layers that were getting in the way. Less code, less cost, less to break. Speed came for free.

This site you're reading is served by a single process. One epoll loop. One worker thread. One core on an Arm machine in a managed Kubernetes cluster. There's no reverse proxy in front of it. No separate TLS terminator. No application server behind it. The same program accepts the TCP connection, does the TLS handshake, parses the HTTP request, looks up the file, and writes the response back to the socket. That's the whole stack.

Under load it serves over 20,000 requests per second on the home page, and about 26,000 per second on a small asset like a stylesheet. Zero pod restarts. Zero timeouts. The 99th-percentile latency, including the full TLS handshake, sits around 60 ms. When the test finishes, the pod's CPU usage drops back to one millicore.

The interesting part isn't the number. It's what the number means: we ran out of network before we ran out of CPU. The pod's network card saturated at about one gigabit per second long before the worker thread broke a sweat. The bottleneck moved out of our software and into the cable.

We removed enough layers that the remaining bottleneck was no longer software. It was physics.

What we actually did

Almost nothing, in lines of code. The real work was subtractive. We removed things:

  • The nginx TLS terminator that used to sit in front of the app.
  • The custom userspace TCP stack we'd built to bypass the kernel.
  • The AF_XDP fast-path that turned out not to work in cloud pod networking anyway.
  • The Linux capabilities the pod no longer needed (NET_RAW, NET_ADMIN, BPF).
  • The proxy hop between the load balancer and the app.
  • The HTTP-01 certificate-renewal indirection — replaced with DNS-01 talking to the zone directly.

What we added was a single file: a small TLS server that owns port 443 directly through normal kernel sockets and feeds the byte-driven TLS engine we already had. Around seven hundred lines. The hard parts had already been written — by the kernel, by Let's Encrypt, by cert-manager, by a TLS engine that didn't care what transport you fed it. Our job was mostly to get out of their way.

Why simple systems end up fast

A "normal" web stack handling 20,000 requests per second is doing an enormous amount of plumbing. The kernel receives a packet, hands it to a virtual ethernet pair, which forwards it through a bridge, through connection tracking, through SNAT at the cloud load balancer, into nginx, which terminates TLS, re-parses the HTTP, opens a backend connection, re-serialises the request, sends it over loopback to an application server, which parses it again, dispatches a route, runs middleware, fetches a body from somewhere, serialises a response, and sends the whole thing back, where the chain unwinds in reverse. Every hop copies bytes, makes syscalls, switches contexts, runs allocators, takes locks. Most of the CPU's budget goes on moving the request around rather than on the request itself.

The whole enchilada

Collapse that chain to one process that owns the socket, the TLS state, the parser and the file table, and the CPU cost per request shrinks until a single Arm core at modest clock can saturate a one-gigabit pipe.

You haven't optimised anything. You've just stopped paying tax.

This is the opposite of the usual scaling story. The usual story says: add a cache, add a CDN, add another replica, add a queue, add a worker pool, add a service mesh, add an observability sidecar. Each addition buys throughput at the cost of more moving parts, more failure modes, more cognitive load, more bill. Subtraction buys the same throughput for nothing. Less surface to break. Less to monitor. Less to upgrade. Less to misconfigure. Less to pay for.

Less waste, more useful work

Every layer you remove is a CPU cycle, a syscall, a page of memory, a watt of power, a millisecond of latency, a category of failure and a paragraph of documentation that you no longer have to spend. That budget doesn't disappear — it becomes available for the only thing that actually matters: serving a useful response to a real user. Simplicity isn't about doing without for its own sake. It's a refusal to keep paying for overhead you never use.

What does that actually cost?

The whole production site — TLS 1.3 engine, every header, every body, every pre-compressed Brotli variant, the metrics page, the lot — runs in about 2.6 MiB of process RSS, inside a container cgroup that sits at ~3 MiB total. The Node.js pod it replaced used 44 MiB to do less. The Kubernetes memory limit on the pod is 128 MiB and is roughly 40× more than the site will ever touch.

To put that into perspective: an empty Python interpreter sat at a bare REPL prompt — no Flask, no Django, no app of any kind — uses about the same amount of RAM. The entire production HTTPS stack for this site has the memory footprint of a language runtime that hasn't yet been asked to do anything.

The shocking part isn't that picoweb is small. It's that the useful-work density is so high that a real, production-grade, interactive TLS site fits into roughly 3 MiB — while heavier stacks spend most of their memory preserving architectural flexibility nobody is using on the hot path.

Same hardware, same file, four servers

To make that claim concrete I deployed four servers side-by-side on the same AKS arm64 node, each given the same wwwroot, the same TLS 1.3 cert and the same Kubernetes resource headroom (50m CPU request, 128 MiB memory limit). One pinned worker each. Then I pointed wrk at each over HTTPS, requesting a small static asset (/fonts/fonts.min.css, 1.3 KB) so the test measured per-request work rather than TLS bulk-encrypt throughput.

Low concurrency, latency-focused (wrk -t2 -c8 -d15s):

Server Req/sec p50 p99
picoweb 34,458 116 µs 5.2 ms
nginx 1.27 18,777 398 µs 1.3 ms
Apache httpd 2.4 10,332 658 µs 3.8 ms
.NET 9 Kestrel 7,486 831 µs 12.9 ms

Saturation, peak memory under load (wrk -t4 -c50 -d30s):

Server Req/sec p50 p99 Peak RAM
picoweb 32,091 667 µs 8.2 ms 14.0 MiB
nginx 1.27 18,710 1.64 ms 3.9 ms 10.5 MiB
Apache httpd 2.4 9,862 2.66 ms 22.7 ms 24.5 MiB
.NET 9 Kestrel 8,548 3.57 ms 11.1 ms 63.1 MiB

The picoweb p50 of 116 microseconds is the headline number: from the wrk client's first byte sent to the last byte of the response received and decrypted, including the full TLS 1.3 record exchange, in roughly the time a modern CPU takes to fetch a cache line from main memory four or five times. Nginx — by any reasonable historical standard the gold standard for a fast static server — sits at 398 µs. Apache at 658 µs. .NET 9 Kestrel, which is itself enormously faster than the .NET of a decade ago, at 831 µs. Picoweb is roughly 3.4× faster than nginx, 5.7× faster than Apache and 7.2× faster than .NET on per-request latency, and the gap widens further on tail percentiles for the heavier stacks. The reason isn't a faster CPU or a fancier TLS library — they all use the same hardware AES. The reason is that picoweb has fewer layers between the syscall and the response.

An earlier run of this benchmark on the much larger /css/wf.css (25 KB) showed picoweb at only ~1.2× nginx in raw requests-per-second. That result was honest but misleading: both servers were saturating the same ~315 MB/s of single-core TLS bulk-encrypt throughput, so the test was measuring AES, not server architecture. Once you drop the payload below the bulk-encrypt floor, the architectural gap re-appears — exactly where you'd expect it to, on the per-request overhead.

And the memory numbers compound the latency story. Picoweb's peak under load is 14 MiB; .NET's is 63 MiB — a 4½× ratio at the top, growing to 7-10× idle. nginx is genuinely brilliant here — at almost thirty years old it lands within touching distance on peak RAM and keeps the tightest p99 of the four. Apache and .NET aren't slow by any normal definition. They're just paying for layers this workload doesn't use, in CPU cycles and in RAM, on every single request.

Speed was the side effect. Simplicity was the work.
The fastest system is usually the one that simply does less nonsense.
