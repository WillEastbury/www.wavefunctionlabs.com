TL;DR — the recipe

Two pieces, both small, both upstream:

  • picoweb — a single-process C server that owns port 443, terminates TLS 1.3 inline, and serves the wwwroot. Two epoll loops, two pinned workers, arena allocation, zero-copy writes, hardware-accelerated crypto. The production server process lives in 23.3 MiB.
  • BareMetalJsTools — the client-side companion. The CSS and JS shipped to the browser. No bundler, no framework, no runtime tax on either end of the wire.

Below: the eleven concrete design choices inside picoweb, the production two-node layout, and the numbers vs nginx, Apache and .NET Kestrel on the same hardware.

This site you're reading is served by a single process. Two epoll loops. Two worker threads, each pinned to one vCPU on a dedicated Arm node in a managed Kubernetes cluster. There's no reverse proxy in front of it. No separate TLS terminator. No application server behind it. The same program accepts the TCP connection, does the TLS handshake, parses the HTTP request, looks up the file, and writes the response back to the socket. That's the whole stack.

Under cross-node load it serves about 50,000 requests per second on a small asset like a stylesheet. Zero pod restarts. Zero timeouts. The 99th-percentile latency, including TLS work and the Kubernetes hop from the load-test node, is 7.9 ms at 50 concurrency and 13.8 ms at 100 concurrency. When the test finishes, the pod's CPU usage drops back to idle.

The interesting part isn't the number. It's what the number means: we removed enough layers that the remaining bottleneck moved out of the web stack. At this point the shape of the AKS nodepool, the benchmark client, the virtual network and the kernel scheduler matter more than framework overhead, because there is no framework overhead left to measure.

We removed enough layers that the remaining bottleneck is network bandwidth, not software.

Step one — delete the standard layers

Before the additive work, the subtractive work. A "normal" web stack handling 20k req/s spends most of its CPU moving the request between processes that re-parse it. The recipe starts by deleting those hops:

  • The nginx TLS terminator that used to sit in front of the app.
  • The proxy hop between the load balancer and the app.
  • The separate application server behind the terminator.
  • The HTTP-01 certificate-renewal indirection — replaced with DNS-01 talking to the zone directly.

In place of all of that: one process that owns port 443, around seven hundred lines of glue around a byte-driven TLS 1.3 engine. The hard parts were already written — by the kernel, by Let's Encrypt, by cert-manager, by a TLS engine that didn't care what transport you fed it. The job was mostly to get out of their way.

Step two — the eleven design choices inside picoweb

The speed isn't one clever trick. It's a handful of small design choices that each remove a category of per-request work, and they compound because they all live in the same process:

  1. The wwwroot is compiled into a jump table at startup. Every file (and every alias — clean URLs, host-vhosting, index-html collapsing) is inserted once into a flat, power-of-two-sized hash slot table. Request dispatch is a hash and an array index. No router framework, no regex, no trie walk, no middleware chain.
  2. Brotli variants are pre-compressed at build time. Every compressible asset is compressed once, into the container image. The hot path picks the right pre-compressed file based on Accept-Encoding and writes it. The most expensive thing a "fast" web server normally does on text payloads — re-compressing every response — simply doesn't happen here.
  3. Response heads and 304 buffers are pre-rendered. For every resource, the full HTTP response head — status line, Content-Type, Content-Length, ETag, cache headers — is built once into a wire-ready buffer at jump-table compile time, along with its matching pre-rendered 304 Not Modified. The hot path picks one of the two buffers and writes it. No header formatting per request.
  4. Dynamic responses use template holes. Endpoints like /stats hold a single fixed-layout wire buffer with known byte offsets for each digit field. The updater overwrites the digits in place; the hot path just writes the buffer. No sprintf, no allocation, no formatting on the hot path.
  5. HTTP/1.1 only, with an inline minimal TLS 1.3. No HTTP/2, no HTTP/3, no general-purpose TLS library — only the records, extensions and ciphersuites actually needed to serve bytes to a modern browser. The TLS state machine is byte-driven and transport-agnostic, so it sits directly on the kernel socket with no buffering layer in between.
  6. One process owns the whole pipeline. Kernel socket → TLS record layer → HTTP parser → jump table → response, all in the same address space. The request never crosses a process boundary, a loopback hop, or a second parser between accept() and the closing TCP FIN.
  7. One event loop per core, each pinned. The production pod runs two worker threads on a 2-vCPU node. Each worker has its own epoll loop, its own SO_REUSEPORT listen socket and its own connection table; the kernel hashes new flows across them. No thread pool, no work-stealing queue, no locks on the hot path. The L1/L2 caches stay warm for the code that actually serves bytes.
  8. No allocation on the hot path. Ever. Connection state is a fixed-size conn_t / kconn_t struct with its 8 KiB read buffer and TLS scratch inline. The whole table is mmap'd once at startup, then MADV_HUGEPAGE'd (TLB-resident), MADV_POPULATE_WRITE'd and memset-walked (every page faulted in), then mlock'd (pinned against reclaim). accept() picks a free slot; close marks it free. Long-lived structures — jump table, response heads, vhost tables, compressed bodies — are bump-allocated out of arenas sized once at boot, then MAP_POPULATE'd and locked the same way. On startup picoweb walks the entire jump table and reads one byte from every response head, body, brotli variant and chrome buffer, so the kernel has faulted every page that the hot path will ever touch before the listen socket comes up. After that point the static-serving path does zero malloc/free and zero minor faults: no allocator lock contention, no fragmentation, no GC pauses, no first-touch latency on the first burst. Resident memory at idle equals resident memory at peak load — the working set is the resident set, and it is the same number whether you've just booted or you're 19,000 requests into a benchmark.
  9. Zero-copy writes straight to the NIC. Above a configurable size threshold, picoweb hands the kernel MSG_ZEROCOPY on send(): the kernel DMAs the response body directly from the user-space buffer into the network card, without copying it into a kernel skbuff first. Below the threshold (where the copy is cheaper than the page-pinning bookkeeping) it falls back to a normal write. There is no userspace memcpy of the response body. Ever.
  10. Hardware-accelerated crypto, hand-vendored. The TLS engine ships its own crypto primitives wired to whatever the CPU actually exposes: SHA-256 via ARMv8 SHA-2 instructions (vsha256hq_u32 / vsha256su1q_u32) on the Arm node it runs on, SHA-NI on x86-64, ChaCha20 with SSE2 / NEON vector paths, AES-GCM with the platform's AES intrinsics, Ed25519 / ECDSA-P256 / RSA-PSS for handshake signing. Detection is runtime via getauxval(AT_HWCAP); the fastest available path wins. No OpenSSL, no libsodium, no FFI hop — the cipher kernels are linked straight into the same binary that owns the socket.
  11. SIMD on the parsing hot paths. Header lowercasing, ASCII scanning, and similar byte-bashing in the HTTP parser use 16-byte NEON on aarch64 and SSE2 on x86-64, with a scalar fallback compiled in for portability. The detected variant is logged at startup so you can see, on any given pod, exactly which path is live.

None of those are novel on their own. The novel part is that they all live in the same process, so the savings compound instead of being eaten by the next layer down.

Step three — prove it on the same hardware

To make the recipe concrete I deployed four servers side-by-side on the same AKS arm64 node, each given the same wwwroot, the same TLS 1.3 cert and the same Kubernetes resource headroom (50m CPU request, 128 MiB memory limit). One pinned worker each. Then I pointed wrk at each over HTTPS, requesting a small static asset (/fonts/fonts.min.css, 1.3 KB) so the test measured per-request work rather than TLS bulk-encrypt throughput.

This is the same site, the same content, the same node it used to run on as a Node.js app behind nginx. The only thing that changed is the server.

Low concurrency, latency-focused (wrk -t2 -c8 -d15s):

Server Req/sec p50 p99
picoweb 34,458 116 µs 5.2 ms
nginx 1.27 18,777 398 µs 1.3 ms
Apache httpd 2.4 10,332 658 µs 3.8 ms
.NET 9 Kestrel 7,486 831 µs 12.9 ms

Saturation, peak memory under load (wrk -t4 -c50 -d30s):

Server Req/sec p50 p99 Peak RAM
picoweb 32,091 667 µs 8.2 ms 13.3 MiB
nginx 1.27 18,710 1.64 ms 3.9 ms 10.5 MiB
Apache httpd 2.4 9,862 2.66 ms 22.7 ms 24.5 MiB
.NET 9 Kestrel 8,548 3.57 ms 11.1 ms 63.1 MiB

The picoweb p50 of 116 microseconds is the headline number: from the wrk client's first byte sent to the last byte of the response received and decrypted, including the full TLS 1.3 record exchange, in roughly the time a modern CPU takes to fetch a cache line from main memory four or five times. Nginx — by any reasonable historical standard the gold standard for a fast static server — sits at 398 µs. Apache at 658 µs. .NET 9 Kestrel, which is itself enormously faster than the .NET of a decade ago, at 831 µs. Picoweb is roughly 3.4× faster than nginx, 5.7× faster than Apache and 7.2× faster than .NET on per-request latency. The reason isn't a faster CPU or a fancier TLS library — they all use the same hardware AES. The reason is that picoweb has fewer layers between the syscall and the response.

About those percentiles. p50 is the median request — what a typical user actually experiences. p99 is the unlucky 1% — the long tail, the request that arrived at a bad moment. In the one-worker comparison above, picoweb wins p50 by a wide margin because the median request hits a hot path with zero allocation, zero copy and one worker doing one thing at a time. nginx edges picoweb on saturation p99 there (3.9 ms vs 8.2 ms) because nginx spreads collisions across workers while the one-worker picoweb harness queues behind one accept loop. Production now runs two pinned workers on a dedicated 2-vCPU node, so the same idea scales across both cores without adding a proxy hop.

An earlier run of this benchmark on the much larger /css/wf.css (25 KB) showed picoweb at only ~1.2× nginx in raw requests-per-second. That result was honest but misleading: both servers were saturating the same ~315 MB/s of single-core TLS bulk-encrypt throughput, so the test was measuring AES, not server architecture. Once you drop the payload below the bulk-encrypt floor, the architectural gap re-appears — exactly where you'd expect it to, on the per-request overhead.

And the memory numbers compound the latency story. The one-worker comparison harness sits at 13.3 MiB. The current production pod runs two pinned workers, so it pays for two preallocated TLS connection tables and sits at 23.3 MiB RSS (VmRSS 23,856 KB, VmHWM 23,856 KB, re-measured on 2026-05-17). The useful invariant is unchanged: memory is allocated, faulted and warmed at startup; under load it stays flat instead of climbing. .NET's peak is 63 MiB — a 3× ratio even against the two-worker production build, and much higher at idle. nginx is genuinely brilliant here — at almost thirty years old it lands within touching distance on peak RAM and keeps the tightest p99 in the single-worker comparison. Apache and .NET aren't slow by any normal definition. They're just paying for layers this workload doesn't use, in CPU cycles and in RAM, on every single request.

Knowing when to stop tuning. The cluster has a hard cost limit: two AKS nodes, each 2-vCPU Arm. That rules out the luxurious shape — two picoweb pods on two clean server nodes plus a third node for the load generator and the rest of the cluster. So the final layout is deliberately simple: vmss000005 is labelled role=server and hard-tainted dedicated=server:NoSchedule; only picoweb tolerates it. vmss000004 is the load-test / co-tenant node. All the low-traffic apps have tiny requests and bin-pack there. Picoweb gets one pod, two pinned workers, and the kernel's SO_REUSEPORT hash does the per-core distribution inside the pod. Azure's load balancer still has sessionAffinity: None; there is just one production endpoint because, on two nodes, a second endpoint would have to share the load-test/co-tenant node.

The honest in-cluster numbers on the final build, measured from a wrk pod pinned to vmss000004 and hitting picoweb on the hard-tainted vmss000005 server node:

Concurrency Req/sec p50 p99 Max
c=20 44,733 1.02 ms 5.54 ms 23.3 ms
c=50 49,975 1.90 ms 7.94 ms 55.5 ms
c=100 50,649 3.44 ms 13.8 ms 110 ms

That is the shape I wanted: about 50k req/s, p99 single-digit milliseconds at c=50, and no hidden proxy layer. To move the p99 lower from here you change the physics around the server — bigger nodes, a third node for the load generator, or a real external client — not the web stack itself. The remaining bottleneck has stopped being software.

Why simple systems end up fast

A "normal" web stack handling 50,000 requests per second is doing an enormous amount of plumbing. The kernel receives a packet, hands it to a virtual ethernet pair, which forwards it through a bridge, through connection tracking, through SNAT at the cloud load balancer, into nginx, which terminates TLS, re-parses the HTTP, opens a backend connection, re-serialises the request, sends it over loopback to an application server, which parses it again, dispatches a route, runs middleware, fetches a body from somewhere, serialises a response, and sends the whole thing back, where the chain unwinds in reverse. Every hop copies bytes, makes syscalls, switches contexts, runs allocators, takes locks. Most of the CPU's budget goes on moving the request around rather than on the request itself.

The whole enchilada

Collapse that chain to one process that owns the socket, the TLS state, the parser and the file table, and the CPU cost per request shrinks until two modest Arm cores can push roughly 50k HTTPS requests per second.

Most of the saving is from deletion. The optimisation on top compounds because the layers it would have had to fight are gone.

This is the opposite of the usual scaling story. The usual story says: add a cache, add a CDN, add another replica, add a queue, add a worker pool, add a service mesh, add an observability sidecar. Each addition buys throughput at the cost of more moving parts, more failure modes, more cognitive load, more bill. Subtraction buys the same throughput for nothing. Less surface to break. Less to monitor. Less to upgrade. Less to misconfigure. Less to pay for.

Less waste, more useful work

Every layer you remove is a CPU cycle, a syscall, a page of memory, a watt of power, a millisecond of latency, a category of failure and a paragraph of documentation that you no longer have to spend. That budget doesn't disappear — it becomes available for the only thing that actually matters: serving a useful response to a real user. Simplicity isn't about doing without for its own sake. It's a refusal to keep paying for overhead you never use.

The three laws, from the bottom up

L3If software is still the bottleneck, there is still a layer to remove.
L2Simple systems do more useful work.
L1Speed is a side effect of simplicity.

What does that actually cost?

The whole production site — TLS 1.3 engine, every header, every body, every pre-compressed Brotli variant, the metrics page, two worker threads, two preallocated connection tables, the lot — runs in 23.3 MiB of process RSS. The Node.js pod it replaced used 44 MiB to do less. The Kubernetes memory limit on the pod is 192 MiB, mostly there as burst headroom rather than expected working set.

To put that into perspective: this is not just the web server binary. It is the TLS engine, all response metadata, all compressed variants, all connection state and all hot-path scratch space, already faulted resident at startup so the first burst of traffic doesn't page the working set in lazily.

The shocking part isn't that picoweb is small. It's that the useful-work density is so high that a real, production-grade, interactive TLS site fits into a few dozen MiB while serving about 50k HTTPS requests per second — while heavier stacks spend most of their memory preserving architectural flexibility nobody is using on the hot path.

Speed was the side effect. Simplicity was the work.

How the site is split — picoweb on the server, BareMetalJsTools in the browser

The recipe above is the server half. The other half lives on the client. Both pieces are small, both are upstream, and both follow the same rule: ship only what runs on the hot path.

Server side
picoweb

Single-process C server. Owns port 443, terminates TLS 1.3 inline, serves the wwwroot. Jump-table routing, pre-rendered heads, pre-compressed Brotli, arena allocation, MSG_ZEROCOPY writes, NEON / ARMv8 SHA-2 / AES-GCM hand-vendored crypto. The eleven choices above, in one binary.

Client side
BareMetalJsTools

The CSS and JS shipped to the browser. No bundler, no framework, no virtual DOM, no runtime. Plain modules and plain stylesheets — the same subtractive rules applied on the other side of the wire. Pre-compressed Brotli by picoweb at build time, served as a static asset.

The split matters. Most "fast" sites move the cost from one side to the other: a tiny server feeding a heavy SPA, or a heavy server feeding a tiny page. This site is small on both ends because the same rule was applied in both places — every layer has to justify the cycles, memory and milliseconds it costs. The pieces are independent (picoweb will serve anything; BareMetalJsTools will run behind any server), but together they're the whole production stack.
