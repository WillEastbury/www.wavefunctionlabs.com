Speed is a side effect

A short essay on what happens when you stop adding layers and start removing them.

simplicity · throughput · TLS · cloud · engineering principles
TL;DR

We rebuilt this site to serve TLS itself, with no proxy in front of it. One process. One core. It now does 20,000+ requests per second and the network runs out before the CPU does. We didn't make anything faster — we just deleted the layers that were getting in the way. Less code, less cost, less to break. Speed came for free.

This site you're reading is served by a single process. One epoll loop. One worker thread. One core on an Arm machine in a managed Kubernetes cluster. There's no reverse proxy in front of it. No separate TLS terminator. No application server behind it. The same program accepts the TCP connection, does the TLS handshake, parses the HTTP request, looks up the file, and writes the response back to the socket. That's the whole stack.

Under load it serves over 20,000 requests per second on the home page, and about 26,000 per second on a small asset like a stylesheet. Zero pod restarts. Zero timeouts. The 99th-percentile latency, including the full TLS handshake, sits around 60 ms. When the test finishes, the pod's CPU usage drops back to one millicore.

The interesting part isn't the number. It's what the number means: we ran out of network before we ran out of CPU. The pod's network card saturated at about one gigabit per second long before the worker thread broke a sweat. The bottleneck moved out of our software and into the cable.

We removed enough layers that the remaining bottleneck was no longer software. It was physics.

What we actually did

Almost nothing, in lines of code. The real work was subtractive. We removed things:

  • The nginx TLS terminator that used to sit in front of the app.
  • The custom userspace TCP stack we'd built to bypass the kernel.
  • The AF_XDP fast-path that turned out not to work in cloud pod networking anyway.
  • The Linux capabilities the pod no longer needed (NET_RAW, NET_ADMIN, BPF).
  • The proxy hop between the load balancer and the app.
  • The HTTP-01 certificate-renewal indirection — replaced with DNS-01 talking to the zone directly.

What we added was a single file: a small TLS server that owns port 443 directly through normal kernel sockets and feeds the byte-driven TLS engine we already had. Around seven hundred lines. The hard parts had already been written — by the kernel, by Let's Encrypt, by cert-manager, by a TLS engine that didn't care what transport you fed it. Our job was mostly to get out of their way.

Why simple systems end up fast

A "normal" web stack handling 20,000 requests per second is doing an enormous amount of plumbing. The kernel receives a packet, hands it to a virtual ethernet pair, which forwards it through a bridge, through connection tracking, through SNAT at the cloud load balancer, into nginx, which terminates TLS, re-parses the HTTP, opens a backend connection, re-serialises the request, sends it over loopback to an application server, which parses it again, dispatches a route, runs middleware, fetches a body from somewhere, serialises a response, and sends the whole thing back, where the chain unwinds in reverse. Every hop copies bytes, makes syscalls, switches contexts, runs allocators, takes locks. Most of the CPU's budget goes on moving the request around rather than on the request itself.

The whole enchilada

Collapse that chain to one process that owns the socket, the TLS state, the parser and the file table, and the CPU cost per request shrinks until a single Arm core at modest clock can saturate a one-gigabit pipe.

You haven't optimised anything. You've just stopped paying tax.

This is the opposite of the usual scaling story. The usual story says: add a cache, add a CDN, add another replica, add a queue, add a worker pool, add a service mesh, add an observability sidecar. Each addition buys throughput at the cost of more moving parts, more failure modes, more cognitive load, more bill. Subtraction buys the same throughput for nothing. Less surface to break. Less to monitor. Less to upgrade. Less to misconfigure. Less to pay for.

Less waste, more useful work

Every layer you remove is a CPU cycle, a syscall, a page of memory, a watt of power, a millisecond of latency, a category of failure and a paragraph of documentation that you no longer have to spend. That budget doesn't disappear — it becomes available for the only thing that actually matters: serving a useful response to a real user. Simplicity isn't asceticism. It's a refusal to keep paying for overhead.

The three laws, from the bottom up

L3If software is still the bottleneck, there is still a layer to remove.
L2Simple systems do more useful work.
L1Speed is a side effect of simplicity.

What does that actually cost?

The whole production site — TLS 1.3 engine, every header, every body, every pre-compressed Brotli and gzip variant, the metrics page, the lot — runs in under 6 MiB of RAM. Resident set is 4.9 MiB for the picoweb process; the whole container cgroup sits at 5.9 MiB. The nginx pod it replaced used 44 MiB to do less. The Kubernetes memory limit is 128 MiB and is roughly 20× more than the site will ever touch.

The shocking part isn't that picoweb is small. It's that the useful-work density is so high that a real, production-grade, interactive TLS site fits into ~6 MiB — while heavier stacks spend most of their memory preserving architectural flexibility nobody is using on the hot path.

Speed was the side effect. Simplicity was the work.
The fastest system is usually the one that simply does less nonsense.

People who built things for a living, on the same point

This isn't a new idea. It's been the working philosophy of more or less every operator who ever shipped a serious system.
